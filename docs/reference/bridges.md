# Bridges

Read this when adapting a robot device or publishing simulated camera results.

## Overview

A bridge translates between robot-facing APIs and the emulator. Device bridges read robot
outputs and write simulated inputs; vision bridges publish camera frames generated by the
simulation. Both live in the robot process. For background, see [how WPILib simulation
works](../concepts/wpilib-simulation.md) and [NetworkTables and simulated
cameras](../concepts/networktables-and-cameras.md). Procedures belong in the [device
guide](../guides/devices.md) and [vision guide](../guides/vision.md).

## Device contract

The extension registers bridge factories through the [built-in
aggregator](../../bridges/builtin_bridges.cpp). A device adapter implements
[IDeviceBridge](../../sdk/include/wpiemu/sdk/devices/device_bridge.h); a camera
encoder implements [IVisionBridge](../../sdk/include/wpiemu/sdk/vision/vision_bridge.h).
SDK interfaces stay independent of HAL, vendor and ntcore APIs.

Signal directions are from the simulator's point of view: `Input` is written to the
robot; `Output` is read from it. A device announcement defines capabilities and an
ordered signal list, and frame indices refer to that list. Re-announcing a device
updates it idempotently. `collectOutputs` appends a full output snapshot; the extension
compresses changes for transport. `applyInputs` receives only devices owned by that
bridge. Unmapped devices use local `applyLoopback`, without an IPC hop.

HAL callbacks can run on robot threads. They must record events only: no blocking, I/O
or `HALSIM_StepTiming` from a callback. The extension's clock thread polls and accesses
bridges while the robot is quiescent. `stop` unregisters callbacks and restores changed
robot-visible state. On reset or a new connection, bridges discard input integration
and unwrap history but preserve discovered devices and robot-owned firmware settings.
Failures are logged and the affected device is skipped; exceptions do not cross SDK
interfaces. See [Extension and IPC](extension-ipc.md) for thread and recovery ownership.

## HAL and vendor devices

`ChannelFamilyBridge` discovers indexed HAL devices by initialized-state polling and
retires them when freed. The [HAL registration](../../bridges/hal/src/registration.cpp)
defines the shipped families. These details affect how robot configurations bind:

- PWM speed is already a normalized robot command. In 2027 it comes from the
  associated motor-controller SimDevice's `Throttle`, including robot-side inversion.
  Raw PWM without that value exposes pulse microseconds, not an invented speed or
  motor capability; position is absent in 2027. DIO direction is fixed at
  discovery; the bridge never writes a robot-configured output pin.
- HAL does not report encoder gearing. Rotation and velocity feedback therefore need
  an injected counts-per-revolution assumption. Encoder reversal is honored. A newly
  initialized zero-frequency duty-cycle sensor gets a connected default.
- A solenoid channel discovered after first `ON` stays latched until its module is
  freed, unless the bridge option enables all channels.
- HAL CAN records sent frames and announces observations later. It does not answer CAN
  traffic or emulate a controller. 2026's callback has no bus identity and uses `rio`;
  2027 carries an observed bus ID (`rio` for 0, `can<N>` otherwise) and up to 64 bytes.
  `lastDataSize` and the sixteen 32-bit data words retain the CAN-FD payload.
  Observing an unknown vendor's frames is not a vendor bridge.
- 2027 omits relay, analog output, built-in accelerometer and controller input-current
  signals. Its onboard IMU accepts acceleration in m/s^2, angles in radians and rates
  in rad/s. The 2026 accelerometer retains its HAL-specific gravity conversion.
- 2027 LED banks expose length and pixel summaries, but no `running` or `outputPort`
  signals: initialization is not a running state, and a bank index is not a physical port.

### Declared CAN address and physical identity

A declared `DeviceKey` includes family, type, ID, bus and channel. A
`PhysicalDeviceId` omits bus because some simulators cannot distinguish devices by
bus. A configured bus label is not evidence that the vendor simulator can distinguish
devices. Shipped CTRE rules use `busIsStatic=false`: SimDevice names do not carry a
bus, so they keep `kBusUnknown`. Do not infer `rio` or CANivore from a static rule.
Runtime hooks may report an observed bus; the hook-provider interface exists, but no
inline-hook provider ships.

Several declared bus addresses can therefore alias one physical device. One mapping is
a warning; independently mapping multiple aliases is a validation error. If a stale
configuration reaches the runtime hub, it treats the conflicted device as unmapped:
slots read neutral values, writes are ignored, local loopback remains active, and an
error is reported. Mappings are retained, so correcting the conflict restores operation.

### Vendor rules and firmware feedback

The shipped vendor bridge adapts Phoenix 5 and Phoenix 6 SimDevices; it is not a
general CAN emulator. A rule matches device names and groups child values. Explicit
bindings convert `canonical = raw * scale + offset` (the inverse on writes).
Unmatched devices and values are ignored. Only a deliberately empty binding table
exposes native names and HAL directions; that fallback does not invent canonical
signals or capabilities. Phoenix 5 exposes its native sensors and a discover-only
Pigeon IMU; it does not use Phoenix 6's input guard or config readback.

The pinned 2027 alpha-7 vendor probe uses official Phoenix 6
`26.70.0-alpha-2` **desktop software simulation**, not substituted 2026 binaries.
The [actual Java robot test](../../app/host/tests/e2e_vendor_2027_test.cpp)
exercises TalonFX duty-cycle/voltage output, mapped mechanism and rotor feedback,
CANcoder direction/offset readback and feedback, Pigeon2 yaw, and process shutdown.
This does not characterize every Phoenix device, closed-loop control mode, C++ vendor
client, operating system or Systemcore hardware. Phoenix 5 is not available for this
2027 preview; REVLib's desktop artifacts alone do not give REV devices a canonical
emulator bridge. REV is still unsupported, not validated through generic CAN traffic.

For Phoenix motors, the emulator drives rotor feedback and firmware applies its own
ratios and offsets. The plant uses firmware-resolved `motorVoltage`; only if that is
absent does the hub fall back to duty cycle times battery voltage. Phoenix
`torqueCurrentReported` is telemetry, not a torque-current request. Using it as a
request would model the controller twice. Robot controller inversion is already in
the output. Physical mounting reversal is separate and belongs to the
[mechanism mapping](mechanisms.md#motor-commands-and-multiple-controllers); do not
invert it again in a vendor rule.

CANcoder feedback is in the calibrated model frame. When a finite magnet offset `o`
and direction sign `s` (`-1` for clockwise-positive, `+1` otherwise) are available,
the bridge writes:

```text
rawPosition = s * (modelPosition - o)
rawVelocity = s * modelVelocity
```

Firmware then reports `s * rawPosition + o`. Use actual readback, including
quantization; do not copy assumed robot constants. Until calibration is usable,
feedback stays raw passthrough, and incomplete or unsupported readback is diagnosed.
Config snapshots are read after discovery while outputs are collected on the quiescent
clock thread, with bounded attempts after the native API becomes available. They are
not continuously refreshed after robot reconfiguration. `poll()` does not call CTRE
native config APIs. Firmware limit-polarity settings are not automatically applied.
Model-side sensor offsets are separate; see [Runtime](runtime.md).

The wrapper appends stable signal indices when a live SimDevice gains values, then
re-announces it. Its Phoenix 6 guard batches raw integrated-sensor inputs, unwraps yaw,
skips unchanged writes and checks readback when committing inputs. Yaw comparisons
treat angles modulo a turn as equivalent; encoder positions do not. Robot
`setYaw`/`setPosition` offsets remain firmware-owned. Persistent competing writes are
diagnosed. Disabling writes for a device also disables its loopback. An optional
mirror-reassert helper is not wired into the shipped extension.

Vendor pacing advice requests at most real time and marks pauses unsafe while devices
are live, but the shipped extension does not apply that advice. Without a HAL backend,
vendor bridges register but discover no devices and warn at startup.

## Vision frame and time contract

The [camera frame](../../sdk/include/wpiemu/sdk/vision/camera_frame.h) is vendor-neutral.
`cameraIndex` indexes `VisionSetup::cameras`; an encoder ignores other camera kinds and
unknown indices. `VisionSystem` captures on simulation ticks, assigns a sequence per
camera, queues configured latency and sends only due frames. `IVisionBridge::apply`
receives that due-only batch; shipped encoders do not reject future
`publishTimeUs` themselves. Reset clears queued captures and restarts sequences.

The producer uses blue-origin NWU field geometry. Its WPILib robot frame is on the
floor below the hull center and uses yaw only, not the chassis COM frame.
`robotToCamera` follows the actual attachment and tilt relative to that frame. Tag
`+X` faces outward; bearing is positive right, elevation positive up, and image pixels
run right and down from the top-left. Visibility checks tag centers for field of view,
range and facing. There is no occlusion or optical distortion. Limelight red-origin
and center-origin pose arrays are derived from the blue-origin pose using the field
size in `VisionSetup` (the plugin's AprilTag layout). If that size is missing or not
finite and positive, only the blue-origin array is published, and the bridge warns
once per configuration. Detections have zero ambiguity. Coprocessor robot poses are
ground truth plus configured noise, not a perspective solve; robot estimators can
still solve from detections.

Publication timestamps use the robot clock, not resettable simulation epoch time.
Bridges sample backend `nowUs()` before HAL stepping; capture time is publication
time minus `max(0, publishTimeUs - captureTimeUs)`. Reset does not rewind HAL's FPGA
clock. Heartbeats advance with simulated time, but are not new captures or proof that
raw results are compatible.

## NetworkTables lifecycle

The [ntcore backend](../../bridges/vision/src/ntcore_backend.cpp) resolves the C API
from the robot's already-loaded ntcore and uses its default instance. It has no
link-time ntcore dependency. Production attaches only; load-if-absent is for
tools/tests, not a private robot runtime. An absent module is retried lazily; missing
required exports instead diagnose and disable the binding. Without the optional
build-time binding, registered vision bridges are unavailable and publish nothing.

`nowUs()` prefers the season's HAL clock (`HAL_GetFPGATime` in 2026,
`HAL_GetMonotonicTime` in 2027), then falls back to `NT_Now`. The bridge interface
remains microseconds: 2027 HAL/ntcore nanoseconds are converted on reads, and publish
timestamps are converted back to native nanoseconds with checked overflow. Publisher options
set `sendAll` and `keepDuplicates`, so unchanged ideal pose arrays still arrive as
timestamped samples. A nonpositive publish timestamp becomes `1` because ntcore
reserves zero for “now”; this is not a general monotonic clamp. Reads copy ntcore-owned
values before disposal. An unassigned value means no request, not a default setting;
subscriber-only topics must not be treated as robot writes.

Configure rebuilds camera state but does not sweep publishers for removed cameras.
Reset republishes empty/no-target results immediately if initialized and available,
otherwise on the next available tick. Stop unpublishes current camera-prefix topics;
the Photon root state is not swept by that loop. The SDK's
[CameraSet](../../sdk/include/wpiemu/sdk/vision/camera_bridge.h) and `CameraBridgeState` own shared configure,
index lookup, reset and heartbeat bookkeeping; each bridge owns its topics and encoding.

## Limelight

The [encoder](../../bridges/vision/src/limelight_bridge.cpp) publishes under
`/limelight` or `/limelight-<name>`. `botpose*` arrays contain six pose values
(meters, roll/pitch/yaw degrees), then latency ms, tag count, span m, mean distance m,
mean area %, then seven values per fiducial:
`id, txnc, tync, areaPercent, distanceToCameraM, distanceToRobotM, ambiguity`.
The largest area is primary. No-target pose arrays are empty, not a zero pose. `tl`
and `cl` each carry half the frame latency; together they reconstruct capture age.
MegaTag 2 arrays contain the same simulated estimate, not an orientation-conditioned
solve.

Blue arrays retain blue-origin poses; red uses the opposite field corner with a
half-turn, and bare `botpose` uses field-center origin. Conversion uses `VisionSetup`
field dimensions, not the layout name. Geometry arrays use pose6 directly in NWU;
there is no extra optical-axis remapping. `camerapose_robotspace` comes from model
frames, not a robot-written transform request. Pipeline index is mirrored; LED,
orientation and crop settings do not change detections. This is an AprilTag encoder,
not a complete Limelight firmware implementation.

## PhotonVision

The [Photon encoder](../../bridges/vision/src/photon_encoding.cpp) defines the packed
schema. `/photonvision/<name>/rawBytes` uses type
`photonstruct:PhotonPipelineResult:4b2ff16a964b5e2bf04be0c1454d91c4`. Its
`message_uuid` property is the JSON string
`"4b2ff16a964b5e2bf04be0c1454d91c4"`. Both must match PhotonLib; a root version or
connected heartbeat alone is insufficient. An initial empty result establishes the
type and property before detections arrive.

The pinned 2027 development version `dev-v2027.0.0-alpha-2-86-gda55d785`
uses UUID `fd353b11f3a818e9c5b457c7dc5a8f5c` in both the type string and
JSON property. Its metadata uses nanoseconds, not microseconds; the bridge converts
its internal microseconds at encoding. Target and multi-tag layouts are unchanged.
This exact version is allowed, not arbitrary 2027 versions or the moving `Dev` tag.

Metadata is four little-endian `i64`s: sequence, capture microseconds, publication
microseconds (nanoseconds for the pinned 2027 schema) and time-since-last-pong (zero).
Transforms encode translation then
quaternion `w,x,y,z`, unlike the SDK's `(x,y,z,w)` member order. Lists have a one-byte
count capped at 127. Optional multi-tag data uses a presence byte and signed 16-bit
fiducial IDs. The [packet contract](../../bridges/vision/include/wpiemu/bridges/vision/photon_encoding.h)
defines the remaining fields. Results use capture sequences, not heartbeat counts.
Multi-tag results need at least two tags and a robot pose; their transform is
field-to-camera and used IDs are sorted.

The bridge checks the encoder's explicit PhotonLib allowlist. An empty project version
uses its built-in default; an unrecognized nonempty version logs an error and suppresses
Photon cameras without disabling Limelight. Similar version numbers do not imply
support. Driver mode produces empty results; 2027's `enabledRequest` also mirrors
to `enabled` and disables detections without dropping the heartbeat. Pipeline, FPS-limit and LED requests
mirror state but do not change capture. Intrinsics are a row-major 3×3 pinhole matrix
with eight zero distortion coefficients. There is no time-sync server, `.schema`
publication, image stream or object-detection pipeline.

Golden vectors and fake publishers do not prove runtime ABI compatibility alone.
The [ntcore smoke tests](../../bridges/vision/tests/ntcore_smoke_tests.cpp) and
[robot integration test](../../app/host/tests/e2e_vision_test.cpp) exercise that
boundary. [Building](../BUILDING.md) owns test commands and Java/C++ sample
prerequisites.

The [2027 vision integration test](../../app/host/tests/e2e_vision_2027_test.cpp)
runs an actual Java PhotonLib client and Limelight NetworkTables reader with a
synthetic two-tag test field, not a production 2027 game plugin. It checks decoded
targets, multi-tag transforms, calibration, capture age, controls, no-target results
and reset epochs. PhotonLib's normal version checks remain enabled.

**2027 C++ PhotonLib is blocked upstream in this pin.** Its
[PhotonCamera::VerifyVersion](https://github.com/PhotonVision/photonvision/blob/da55d785/photon-lib/src/main/native/cpp/photon/PhotonCamera.cpp)
assigns 2027 ntcore's JSON-text `GetProperty("message_uuid")` result to a JSON
string instead of parsing it. It then compares the unquoted local UUID with a
remote UUID that still contains quotes and throws, despite identical definitions.
The C++ sample reproduces that failure. Publishing invalid JSON, suppressing version
checks or claiming a connected heartbeat as compatibility would conceal the bug;
none is used. Retest with a fixed upstream PhotonLib before claiming 2027 C++ support.
