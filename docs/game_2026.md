# game_2026 – REBUILT (2026) year plugin

Everything season-specific lives in `plugins/game_2026/` (target `wpiemu_plugin_game_2026`, links **only**
`wpiemu_sdk`). Core, app and the other plugins know nothing about it; it is selected by
`RobotConfig::project.wpilibYear == 2026` through `GamePluginRegistry` and registered by the one line in
`plugins/builtin_plugins.cpp`.

toward the red wall, +Y left, origin at the blue/low-Y corner of the carpet).

## 2. Field

Authored once for the **blue** alliance and rotated 180° about the field centre for **red**; a test asserts the
mirror (`field layout` tests). Data tables, no mesh assets: `include/.../field_dimensions.h` (constants with
source tags), `field_layout.{h,cpp}` (pure `FieldLayout` builder + `Game2026Field`, the RAII owner of the colliders).

| Element | Modelled as | Dimensions (source) |
|---|---|---|
| Carpet | static box, top at z = 0, extends 3 m past the field | field 16.541 x 8.069 m [AT]/[GM] 5.2 |
| Guardrails | boxes along both long edges | 20.0 in tall [GM] 5.2 (fuel can leave over them, like the real field) |
| Alliance walls | boxes behind x = 0 / x = L, 2.0 m tall; one segment set per alliance with the outpost corral opening cut out | opening 32.0 in x 7.0 in, 1.88 in off the floor [GM] 5.9.2 |
| Hub | hollow tube: base block (0.6 m) + four 5 cm walls up to **72 in**, 47 in square | 47 x 47 in, opening front edge 72 in [GM] 5.4; centre x = 4.6256 m (blue) / y = 4.0345 m [AT],[MS]; faces at 4.029 / 5.223 m = the 158.6 in starting line [GM] |
| Hub scoring sensor | sensor box inside the tube, 0.84 x 0.84 x 0.4 m centred at z = 1.55 m, below the rim | >= 0.3 m deep because sensors have no CCD ([ADR]) |
| Hub exits | four exit points on the neutral-zone face, 2 m/s, -15°, fan ±11.25° / ±33.75° | [MS]; height 0.6 m ("exits at the base" [GM] 5.4) |
| Bump | closed triangle mesh (pentagonal prism): two **15°** ramps meeting in a ridge | 73.0 in wide (Y), 44.4 in deep (X), ridge **6.513 in** [GM] 5.5; edge step 0.5 in derived so that 15° ramps over half the depth reach the stated ridge; 2 per alliance, adjacent to the hub |
| Trench | arm box (underside **22.25 in**, top **40.25 in**, 47 in deep) + support post next to the bump | free width under the arm 50.34 in [GM] 5.6, 12 in post [MS]; arm runs from the guardrail to the bump; 2 per alliance |
| Tower | base plate, two uprights (3.5 x 1.5 x 72.1 in, 33.75 in apart), three rungs (1.66 in OD pipe) at **27 / 45 / 63 in** | [GM] 5.8; centre y = 3.7437 m (blue) [AT],[MS]; upright x = 1.062 m [MS] |
| Depot | three 3 in x 1.125 in barriers (front + two sides) | 42 x 27 in [GM] 5.7; centre y = 5.987 m [MS] |
| Outpost | opening in the wall + a **corral** sensor volume behind it (35.8 in wide, 37.6 in deep) + a chute exit point | [GM] 5.9.2; centre y = 0.666 m [AT],[MS] |

`FieldDescription::visuals` carries the same boxes/cylinders (plus ramp slabs for the bumps) for the renderer.
If an adapter refuses `MeshShape` the bump is rebuilt from a base block and two tilted slabs (tested).
The Box3D integration test (`test_box3d_integration.cpp`) ray-casts the real engine against these surfaces
(carpet, 15° slope with the right normal, trench clearance, hub faces, rung height).

Collision categories: field shapes `layer::Field`, sensors `layer::Sensor` (mask `layer::Fuel`), fuel `layer::Fuel`
with mask `Field | Robot | Fuel | Sensor` (ADR 0003: **the fuel mask must include the sensor bit**). The robot
chassis shape is core's `layer::Robot`; its mask must include `layer::Fuel` so robots push fuel.

## 3. Fuel

* Sphere, **r = 0.075 m** (5.91 in / 15.0 cm [GM] 5.10.1), **0.215 kg** (mid of 0.203–0.227 kg [GM]) - density derived
  from the configured mass; friction 0.6, restitution 0.55, rolling resistance 0.02 ([ADR]); all configurable
  (`fuelMassKg`, `fuelFriction`, `fuelRestitution`, `fuelRollingResistance`). MapleSim uses restitution 0.8; the
  ADR value is a conservative default for foam.
* Bodies are dynamic with `allowSleep` (config `fuelSleeping`), so a 400-ball pile costs almost nothing once settled.
  Shots are created with the *bullet* flag.
* Spawn/despawn is the `FuelPool` (slot reuse, a body cap `maxFuelOnField`, RAII cleanup). The fuel id travels in
  the shape `userTag`, which is how hub/corral sensor events find the fuel again.
* **Initial layout** [GM] 6.3.4: 24 in each depot (4 x 6 grid), neutral zone **12 columns x N rows** centred on the field
  (360 by default = the usual staging with all six robots preloaded; up to 408), 24 in each outpost chute (kept as a
  *stock*, not as bodies), **8 preloaded** in the robot (the meter). Counts are config.
* Fuel that leaves the play area (more than 2 m outside the carpet rectangle) is despawned and counted as lost.

## 4. Rules implemented

### Match timeline [GM] 6.4, Table 6-2

| Period | Phase | Length |
|---|---|---|
| AUTO | AUTO | 20 s |
| TELEOP | TRANSITION | 10 s |
| | SHIFT 1..4 | 25 s each |
| | END GAME | 30 s |

`MatchClock` (`match_clock.h`) derives the phase from the SDK driver-station state: enabled + mode select AUTO or
TELEOP; time is `DsState::matchTimeS` when `>= 0` (**WPILib convention: seconds remaining in the period, counting
down**), otherwise the clock integrates the sim step while the robot is enabled in that mode. Disabled time does not
advance the clock. Test mode = practice (both hubs active, no match structure).

### Hub status [GM] 6.4.1, Table 6-3

Both hubs are active in AUTO, TRANSITION and END GAME. In SHIFT 1..4 exactly one is active: the alliance that scored
**more fuel in AUTO** has its hub **inactive in SHIFT 1**, active in 2, inactive in 3, active in 4. The first-inactive
alliance is latched when TELEOP starts, from (in priority): the config override `firstInactiveHub`
(`red`/`blue`), the FMS game-data character in `DsState::gameSpecificMessage` (`R`/`B`), the auto fuel counts (tie:
seeded random from `SimContext::rng()`). Setting `enforceHubShifts = false` makes both hubs score whenever the robot
is enabled (quick tests).

### Scoring [GM] 6.5, Table 6-4

A fuel is scored when it enters a hub's scoring sensor (the top opening). **1 point** per fuel while the hub is active
(AUTO and TELEOP alike), tracked per alliance and split into `autoFuel` / `teleopFuel` / `inactiveFuel`. Fuel entering
an inactive hub earns nothing but is still processed. **Grace [GM] 6.5**: assessment continues 3 s after a hub
deactivates or a period ends; fuel scored in that window after AUTO counts as AUTO. Scored fuel waits
`hubProcessingDelayS` (1 s) and leaves through one of the four exits into the neutral zone (`recycleScoredFuel`).
If the body cap is full or the physics backend refuses a release, the fuel stays pending and retries
on subsequent ticks. A refused release stops further spawn attempts for that tick, preserving fuel
without unbounded retry work; successful releases still respect `maxFuelOnField`.
Tower points, ranking points, G-rules and penalties are out of scope (HUD-only, per the project decisions).

### Outposts

Fuel pushed through the base opening enters the corral sensor and joins that alliance's chute stock (HUD value).
`humanPlayer = timed` releases one chute fuel every `humanPlayerPeriodS` while a match period is running; `off`
(default) never does.

## 5. Robot side: meter, intake, shooter

The plugin does **not** duplicate the generic mechanisms. The user builds a normal roller / flywheel / indexer / hood /
turret with the core templates and maps their devices; two lightweight, slot-less wrapper templates bind those
mechanisms to the game. They read other mechanisms' published `MechanismState` (named values, converted to SI from
`NamedValue::unit`: `rad`, `deg`, `rpm`, `rot/s`, ...) through `IMechanismDirectory`, so any template that publishes
the value works.

### `game_2026.fuel_intake` (category Intake)

| Property | Meaning |
|---|---|
| `pickupZone` (Box3, mechanism frame) | fuel **centres** inside it are absorbed; moves with the mechanism mount/attachment (`linkPoseInChassis`) |
| `activation` | `roller` (default), `deployed`, `roller_and_deployed`, `roller_or_deployed`, `always` |
| `rollerMechanism` / `rollerValue` / `rollerThreshold` | roller counts as spinning when `|value|` (SI) >= threshold; empty mechanism id = condition always true |
| `deployMechanism` / `deployValue` / `deployedPosition` / `deployedTolerance` | deployed when `|value - position| <= tolerance` (or the mechanism's `active` flag if the value is not published) |
| `intakeRateHz` | max fuel per second per intake (0 = unlimited); a token bucket, primed when idle |

The game state absorbs (despawns) fuel in the zone **only while active and the meter is below `capacity`**, nearest to
the zone centre first. Fuel outside the zone is simply pushed around by the robot (real physics) and can be collected
again later.

### `game_2026.fuel_shooter` (category Shooter, link `muzzle`)

| Group | Properties |
|---|---|
| Muzzle | `muzzleOffset` (mechanism frame; +X = shooting direction at zero yaw) |
| Flywheel | `flywheelMechanism`, `flywheelValue`, `flywheelRadiusM`, `efficiency`, `fixedExitSpeedMps`, `minExitSpeedMps` - **exit speed = |omega| x radius x efficiency** |
| Aim | `hoodAngleRad` (elevation; offset when a hood is named), `hoodMechanism/Value/Gain`, `turretMechanism/Value/Gain`, `turretYawOffsetRad` - or attach the shooter to the turret **link** |
| Feed | `feedMechanism`, `feedValue`, `feedThreshold`, `fireRateHz` - fires while the feed mechanism's `|value|` >= threshold (empty reference: whenever the flywheel is up to speed) |
| Dispersion | `exitSpeedJitter`, `aimJitterRad` (seeded `Rng`), `inheritRobotVelocity` |

While *feeding*, `fireRateHz` fuel/s are launched as **real physics bodies** from the muzzle (direction from hood +
turret + robot heading, velocity = exit velocity along it **plus the muzzle's own velocity**) as long as the meter is
not empty. Shot fuel ignores the robot's collision shapes for `shotGhostS` (0.15 s) so it does not collide with the
shooter that fired it. Published values: `feeding`, `exitSpeed`, `elevation`, `yaw`; link pose `muzzle`.

A nonempty reference to a mechanism that does not exist logs one warning and keeps the intake/shooter
inactive, including a named hood or turret. Empty optional aim/feed references remain valid. A positive
`fixedExitSpeedMps` bypasses the flywheel reference, so that unused reference need not resolve.

**Using the core templates** (`core/mechanisms`, tested end to end in `test_core_mechanisms_integration.cpp`):

| User mechanism (core type) | Published values the wrappers read | Typical wrapper setting |
|---|---|---|
| `roller`, `indexer`, `shooter` (flywheel), `generic_1dof` | `velocity` (rad/s), `position` (rad) | `rollerMechanism = "<id>"` (default value name `velocity`), `flywheelMechanism = "<id>"`, `feedMechanism = "<id>"` |
| `pivot` (hood), `turret` | `position` (rad) | `hoodMechanism` / `turretMechanism` (default value name `position`) |
| `intake` (deploy arm + roller) | `rollerVelocity` (rad/s), `deployed` (0/1), `deployPosition` | `rollerMechanism = "<id>"`, `rollerValue = "rollerVelocity"`, `deployMechanism = "<id>"`, `deployValue = "deployed"`, `deployedPosition = 1`, `deployedTolerance = 0.5` |

`RobotConfig::plugins["game_2026"]` (`data`, schema version **2**) – property table = `contributeConfigSchema()`:

| Key | Default | Range | |
|---|---|---|---|
| `capacity` | 30 | 0..500 | fuel meter capacity |
| `preloadFuel` | 8 | 0..500 (limited to capacity) | meter at match start |
| `neutralFuel` | 360 | 0..408 | neutral zone staging |
| `depotFuel` | 24 | 0..24 | per depot |

| `maxFuelOnField` | 800 | 0..5000 | body cap |

## 7. HUD, editor panels, snapshot

`IGameState::publish` adds an entity group `fuel` (instanced spheres) and these HUD values (all under `game_2026.`):
`fuel.count`, `fuel.capacity`, `fuel.on_field`, `fuel.shots`, `score.red`, `score.blue`, `hub.red.active`,
`hub.blue.active`, `hub.own.active` (own alliance from the DS station), `hub.first_inactive`, `match.phase`,
`match.period_remaining` (s), `match.phase_remaining` (s), `outpost.red.stock`, `outpost.blue.stock`.
`contributeHud()` binds them to widgets (fuel meter with `maxKey`, match timer, phase text, hub badges, scores,
shot/field counters). `contributeEditorPanels()` gives three plugin-config panels (fuel meter, field staging,
match rules) and two mechanism panels with viewport overlays (pickup zone Box3, muzzle offset Vec3). A test checks
that every widget value and every panel/overlay key exists.

## 8. Config versions and migration

* **v2** (current): the layout above.
* **v1**: the pre-release draft layout (flat keys `fuelCapacity`, `preload`, `neutralZoneFuel`, `depotCount`,
  `hubShifts`, `firstInactive`; mechanism types `game_2026.intake` / `game_2026.shooter` with draft property
  names). Never documented as stable; kept as the worked example of the migration machinery.

`configMigrators()` returns `ConfigV1ToV2Migrator` (section data). `migrateRobotConfig()` (SDK 1.1) renames the draft
mechanism types/properties, **only for mechanisms this plugin owns** (`ownsMechanismType`), idempotently. Adding v3 =
a new `IConfigMigrator` + `kConfigSchemaVersion` bump.

## 9. Runtime contract

What the sim runtime / app must (and does not yet have to) provide - see also `docs/ARCHITECTURE.md` §4:

1. `IGameModule::createField` before `createGameState`; call `IGameState::reset` before the first tick and on Reset
   (the state is also valid right after construction). `step` runs **after** the physics step (it consumes that step's
   sensor events); mechanisms tick **before** it (they publish `active`/`feeding`).
2. `SimContext::mechanisms()` bound before the first `step` (the state looks for the plugin's mechanisms every tick);
   the chassis `BodyId` bound for robot pose/velocity (without it the robot is at the origin and has no velocity).
3. The chassis collision shape must use `layer::Robot` with a mask that includes `layer::Fuel`.
4. `DsState::matchTimeS` = seconds **remaining** in the current period (WPILib), or `-1` to use the integrated clock.
5. FMS game data: robot code reads `DriverStation.getGameSpecificMessage()` ('R'/'B' = the alliance whose hub goes
   inactive first, available from the start of TELEOP) to learn the hub order. The plugin latches that alliance (HUD
   `game_2026.hub.first_inactive`) and exposes it through `IGameState::gameSpecificMessage()` (`R`/`B`, `nullopt` before
   TELEOP and after Reset); `core/runtime` (`SessionRunner`) overlays it on `DsState::gameSpecificMessage`
   and re-sends the DS state when it changes. It wins over the DS panel's manual game-message text.

## 10. Simplifications (honest list)

* No official CAD: dimensions outside the manual text come from the AprilTag layout and MapleSim (marked above);
  expect centimetre-level, not millimetre-level, agreement. The hub is a rectangular tube of the stated 47 in
  footprint and 72 in rim height - the hexagonal funnel, the hub's internal ramps/sensor array and the **back net**
  are not modelled (overshot shots simply fly on). Hub exit positions/velocities are MapleSim's, at an approximate height.
* Tower: base plate, uprights and rungs only (no support structure, no climb scoring / TOWER points / ranking points).
* Trench: arm + one post per side; the hinged pivot arm and electronics are not modelled. Wall/driver-station
  geometry is solid boxes.
* Bumps use the stated ridge/width/depth with a derived 0.5 in edge step; the ramp thickness is not modelled.
* Depot barrier and outpost positions (y) are from MapleSim/AprilTags to a few centimetres. Outposts: corral
  delivery and a timed human player only; the chute door, the human player throwing fuel at the hub and the 3-second
  scoring-table behaviour of the real field are not simulated.
* Fuel is a rigid sphere (no wear/deformation, no compression against the flywheel); exit speed is
  `omega x r x efficiency`, not a contact model.
* The game logic is for a single robot (`SimContext::chassisBody`); other robots would need their own meters.
* The AUTO winner is decided from fuel scored by the simulated alliances only (opponent fuel is whatever the user
  places), ties are seeded random as the real FMS.
