# game_2026 – REBUILT (2026) year plugin

Everything season-specific lives in `plugins/game_2026/` (target `wpiemu_plugin_game_2026`, links **only**
`wpiemu_sdk`). Core, app and the other plugins know nothing about it; it is selected by
`RobotConfig::project.wpilibYear == 2026` through `GamePluginRegistry` and registered by the one line in
`plugins/builtin_plugins.cpp`.

`FieldDescription::visuals` carries the same boxes/cylinders (plus ramp slabs for the bumps) for the renderer.
If an adapter refuses `MeshShape` the bump is rebuilt from a base block and two tilted slabs (tested).
The Box3D integration test (`test_box3d_integration.cpp`) ray-casts the real engine against these surfaces
(carpet, 15° slope with the right normal, trench clearance, hub faces, rung height).

Collision categories: field shapes `layer::Field`, sensors `layer::Sensor` (mask `layer::Fuel`), fuel `layer::Fuel`
with mask `Field | Robot | Fuel | Sensor` (ADR 0003: **the fuel mask must include the sensor bit**). The robot
chassis shape is core's `layer::Robot`; its mask must include `layer::Fuel` so robots push fuel.

### AprilTag layout (vision)
`IGameModule::aprilTagLayout()` returns the **`2026-rebuilt-welded`** layout from the WPILib `apriltag` 2026.2.1 data [AT]: the 32
tags with their ids, their poses in the field frame (centre of the tag, +X out of its face) and the field size, embedded in the
plugin in `src/april_tags.cpp` (no file is read at run time; `tests/game_2026/test_april_tags.cpp` checks it against the JSON). The
simulated Limelight / PhotonVision cameras ([vision.md](vision.md)) use it; the plugin does no vision logic itself. The run view
shows the tags as markers.
## 3. Fuel

* Sphere, **r = 0.075 m** (5.91 in / 15.0 cm [GM] 5.10.1), **0.215 kg** (mid of 0.203–0.227 kg [GM]) - density derived
  from the configured mass; friction 0.6, restitution 0.55, rolling resistance 0.02 ([ADR]); all configurable
  (`fuelMassKg`, `fuelFriction`, `fuelRestitution`, `fuelRollingResistance`). MapleSim uses restitution 0.8; the
  ADR value is a conservative default for foam.
* Bodies are dynamic with `allowSleep` (config `fuelSleeping`), so a 400-ball pile costs almost nothing once settled.
  Shots are created with the *bullet* flag.
* Spawn/despawn is the `FuelPool` (slot reuse, a body cap `maxFuelOnField`, RAII cleanup). The fuel id travels in
  the shape `userTag`, which is how hub/corral sensor events find the fuel again.
* **Initial layout** [GM] 6.3.4: 24 in each depot (4 x 6 grid), neutral zone **12 columns x N rows** centred on the field
  (360 by default = the usual staging with all six robots preloaded; up to 408), 24 in each outpost chute (kept as a
  *stock*, not as bodies), **8 preloaded** in the robot (the meter). Counts are config.
* Fuel that leaves the play area (more than 2 m outside the carpet rectangle) is despawned and counted as lost.

## 4. Rules implemented

### Match timeline [GM] 6.4, Table 6-2

| Period | Phase | Length |
|---|---|---|
| AUTO | AUTO | 20 s |
| TELEOP | TRANSITION | 10 s |
| | SHIFT 1..4 | 25 s each |
| | END GAME | 30 s |

`MatchClock` (`match_clock.h`) derives the phase from the SDK driver-station state: enabled + mode select AUTO or
TELEOP; time is `DsState::matchTimeS` when `>= 0` (**WPILib convention: seconds remaining in the period, counting
down**), otherwise the clock integrates the sim step while the robot is enabled in that mode. Disabled time does not
advance the clock. Test mode = practice (both hubs active, no match structure).

### Hub status [GM] 6.4.1, Table 6-3

Both hubs are active in AUTO, TRANSITION and END GAME. In SHIFT 1..4 exactly one is active: the alliance that scored
**more fuel in AUTO** has its hub **inactive in SHIFT 1**, active in 2, inactive in 3, active in 4. The first-inactive
alliance is latched when TELEOP starts, from (in priority): the config override `firstInactiveHub`
(`red`/`blue`), the FMS game-data character in `DsState::gameSpecificMessage` (`R`/`B`), the auto fuel counts (tie:
seeded random from `SimContext::rng()`). Setting `enforceHubShifts = false` makes both hubs score whenever the robot
is enabled (quick tests).

### Scoring [GM] 6.5, Table 6-4

A fuel is scored when it enters a hub's scoring sensor (the top opening). **1 point** per fuel while the hub is active
(AUTO and TELEOP alike), tracked per alliance and split into `autoFuel` / `teleopFuel` / `inactiveFuel`. Fuel entering
an inactive hub earns nothing but is still processed. **Grace [GM] 6.5**: assessment continues 3 s after a hub
deactivates or a period ends; fuel scored in that window after AUTO counts as AUTO. Scored fuel waits
`hubProcessingDelayS` (1 s) and leaves through one of the four exits into the neutral zone (`recycleScoredFuel`).
If the body cap is full or the physics backend refuses a release, the fuel stays pending and retries
on subsequent ticks. A refused release stops further spawn attempts for that tick, preserving fuel
without unbounded retry work; successful releases still respect `maxFuelOnField`.
Tower points, ranking points, G-rules and penalties are out of scope (HUD-only, per the project decisions).

### Outposts

Fuel pushed through the base opening enters the corral sensor and joins that alliance's chute stock (HUD value).
`humanPlayer = timed` releases one chute fuel every `humanPlayerPeriodS` while a match period is running; `off`
(default) never does.

## 5. Robot side: meter, pickup zones, shooter zones

The plugin ships **no mechanism templates**. The user builds normal `mechanism`s (rotary roller / flywheel / indexer, arm hood,
rotary turret) with the core template and maps their devices; the game binds to them through two **robot zones**
([ADR 0016](decisions/0016-zones.md), `RobotConfig::zones`, `sdk/config/zone.h`). A zone is a game-owned place on the
robot (a volume or a muzzle) with

* an `id`, a `label` and a `kind` the plugin owns (`game_2026.pickup`, `game_2026.shooter`);
* an **attachment** (`attachment.parentMechanismId` = `"chassis"`/empty or a mechanism id, `attachment.parentLink`) and a
  `local` pose: the zone pose in the chassis frame is `linkPoseInChassis(parent, link) * local` (identity for the chassis,
  and also when the mechanism/link cannot be resolved), so a zone follows e.g. a deploying intake arm or a turret link;
* `sizeM` (full extents; volume kinds only) and kind-specific `properties`, validated against the kind's schema
  (`contributeZoneKinds()`; defaults are filled in by the config pipeline);
* an **activation**: `mode` (`all` = AND, `any` = OR) and a list of conditions on values other mechanisms publish
  (`MechanismState::values`, converted to SI from `NamedValue::unit`: `rad`, `deg`, `rpm`, `rot/s`, ...): `mechanismId`,
  `value` (default `velocity`), `op` (`above`, `below`, `within`), `threshold`, `tolerance`, `absolute` (compare `|v|`).
  An empty list is always active. Evaluation is `sdk::evaluateActivation`: a condition on an unknown mechanism is false
  and logs **one warning per mechanism id and zone**; a mechanism that does not publish the value falls back to its
  `active` flag.

`Game2026State` builds the runtime object of every zone whose kind it owns from `SimContext::config().zones` (constructor
and `reset`; other kinds are ignored). Every `step` it resolves each zone's pose, evaluates its activation, updates the
runtime (rate limiters, aim) and then runs the shooters, then the pickups. Mechanisms tick **before** the game state, so the
values the conditions read are fresh. `publish` adds `ZoneState{id, active}` for every owned zone (`ISimSnapshot::zones()`);
`active` is "the activation currently holds" (for a shooter that is the feed condition, not whether it can fire right now).

### `game_2026.pickup` (shape volume; default size 0.30 x 0.60 x 0.30 m at local (0.45, 0, 0.15))

| Property | Default | Meaning |
|---|---|---|
| `intakeRateHz` | 15 (0..1000) | max fuel per second absorbed by this pickup (0 = unlimited); a token bucket, primed while idle |

The game state absorbs (despawns) fuel whose **centre** is inside the zone box (zone frame) **only while the zone is active and
the meter is below `capacity`**, nearest to the zone centre first. Fuel outside the zone is simply pushed around by the robot
(real physics) and can be collected again later. Typical activation: roller `velocity` above 20 rad/s, optionally AND the
intake arm `position` within a tolerance of its deployed angle (`within`); `any` for "either".

### `game_2026.shooter` (shape muzzle; default local pose (0.25, 0, 0.55); muzzle direction = local +X)

| Group | Properties |
|---|---|
| Flywheel | `flywheelMechanism`, `flywheelValue` (`velocity`), `flywheelRadiusM` (0.0508), `efficiency` (0.6), `fixedExitSpeedMps` (0), `minExitSpeedMps` (2) - **exit speed = \|omega\| x radius x efficiency** from the flywheel mechanism's reading, or `fixedExitSpeedMps` when > 0 |
| Aim | `hoodAngleRad` (elevation, 1.047; offset when a hood is named), `hoodMechanism`, `hoodValue` (`position`), `hoodGain` (1), `turretMechanism`, `turretValue` (`position`), `turretGain` (1), `turretYawOffsetRad` (0) |
| Fire | `fireRateHz` (10) |
| Dispersion | `exitSpeedJitter` (0), `aimJitterRad` (0) (seeded `Rng`), `inheritRobotVelocity` (true) |

Elevation = `hoodAngleRad + hoodGain x hood value`, yaw = `turretYawOffsetRad + turretGain x turret value`, applied to the zone's
+X axis. The zone pose already includes its attachment link, so attaching the shooter to a **turret link** rotates the muzzle
with no `turretMechanism`. The old "feed" mechanism is now the zone's activation (e.g. indexer `velocity` above 5 rad/s); an empty
activation fires whenever the flywheel is up to speed.

A shooter fires `fireRateHz` fuel/s as **real physics bodies** from the zone origin (direction from the zone pose, hood and
turret, velocity = exit velocity along it **plus the muzzle's own velocity** when `inheritRobotVelocity`) while its activation
holds **and** the exit speed is `>= minExitSpeedMps` **and** the meter is not empty. Several shots in one tick leave one ball
diameter apart along the barrel. Shot fuel ignores the robot's collision shapes for `shotGhostS` (0.15 s) so it does not collide with the
shooter that fired it.

A nonempty reference (flywheel, hood, turret) to a mechanism that does not exist logs one warning and keeps that shooter
silent, as does an unknown mechanism in its activation. Empty optional references remain valid. A positive `fixedExitSpeedMps`
bypasses the flywheel reference, so that unused reference need not resolve.

**Using the core templates** (`core/mechanisms`, tested end to end in `test_core_mechanisms_integration.cpp`):

| User mechanism (core `mechanism`, Motion) | Published values | Typical zone setting |
|---|---|---|
| rotary roller / indexer / flywheel | `velocity` (rad/s), `position` (rad) | pickup condition `roller velocity above 20`; shooter condition `indexer velocity above 5`, `flywheelMechanism = "<id>"` |
| arm hood, rotary turret | `position` (rad) | `hoodMechanism` / `turretMechanism` (value name `position`) |
| deploying intake = an **arm** mechanism + a rotary roller | arm `position` (rad); roller `velocity` | pickup activation `all`: `roller velocity above 20` and `arm position within 0.1 of <deployed rad>`; attach the pickup to the arm link to move it with the arm |

There is no core intake: an intake is a rotary mechanism (plus an arm mechanism when it deploys), see
[ADR 0015](decisions/0015-single-mechanism-template.md).

|---|---|---|---|
| `capacity` | 30 | 0..500 | fuel meter capacity |
| `preloadFuel` | 8 | 0..500 (limited to capacity) | meter at match start |
| `neutralFuel` | 360 | 0..408 | neutral zone staging |
| `depotFuel` | 24 | 0..24 | per depot |

| `enforceHubShifts`, `firstInactiveHub`, `hubProcessingDelayS`, `recycleScoredFuel` | true, `auto`, 1.0, true | | rules |

Missing keys take defaults, out-of-range values are clamped (`parseConfig`); the core validator uses the same schema.

config pipeline (unknown kinds of this plugin are warned about, kinds of other plugins are errors). There is no
conversion from the former `game_2026.fuel_intake` / `game_2026.fuel_shooter` mechanisms (ADR 0013).

## 7. HUD, editor panels, snapshot

`IGameState::publish` adds an entity group `fuel` (instanced spheres), one `ZoneState{id, active}` per owned zone
(`ISimSnapshot::zones()`, `active` = the zone's activation holds) and these HUD values (all under `game_2026.`):
`fuel.count`, `fuel.capacity`, `fuel.on_field`, `fuel.shots`, `score.red`, `score.blue`, `hub.red.active`,
`hub.blue.active`, `hub.own.active` (own alliance from the DS station), `hub.first_inactive`, `match.phase`,
`match.period_remaining` (s), `match.phase_remaining` (s), `outpost.red.stock`, `outpost.blue.stock`.
`contributeHud()` binds them to widgets (fuel meter with `maxKey`, match timer, phase text, hub badges, scores,
shot/field counters). `contributeEditorPanels()` gives three plugin-config panels only (fuel meter, field staging, match
rules); the pickup volume and the muzzle are edited as zones from `contributeZoneKinds()` (display name, description,
shape, property schema, default size/pose, gizmo colour `#44cc66` pickup / `#ff7043` shooter). A test checks
that every widget value and every panel/overlay key exists.

## 8. Config version

The section is written with `schemaVersion: 1` (`kConfigSchemaVersion`). Until release the SDK stays at version 1 and
there is no migration (ADR 0013): a section with any other version is refused (`VersionMismatch`).
## 9. Runtime contract

What the sim runtime / app must (and does not yet have to) provide - see also `docs/ARCHITECTURE.md` §4:

1. `IGameModule::createField` before `createGameState`; call `IGameState::reset` before the first tick and on Reset
   (the state is also valid right after construction). `step` runs **after** the physics step (it consumes that step's
   sensor events); mechanisms tick **before** it (so the values zone activations and shooters read are fresh).
2. `SimContext::mechanisms()` bound before the first `step` (zone activations, aim references and attachment links are
   resolved through it every tick; without it every condition on a mechanism is false and zones sit on the chassis);
   `SimContext::config().zones` holds the zones (read in the constructor and `reset`); the chassis `BodyId` bound for
   robot pose/velocity (without it the robot is at the origin and has no velocity).
3. The chassis collision shape must use `layer::Robot` with a mask that includes `layer::Fuel`.
4. `DsState::matchTimeS` = seconds **remaining** in the current period (WPILib), or `-1` to use the integrated clock.
5. FMS game data: robot code reads `DriverStation.getGameSpecificMessage()` ('R'/'B' = the alliance whose hub goes
   inactive first, available from the start of TELEOP) to learn the hub order. The plugin latches that alliance (HUD
   `game_2026.hub.first_inactive`) and exposes it through `IGameState::gameSpecificMessage()` (`R`/`B`, `nullopt` before
   TELEOP and after Reset); `core/runtime` (`SessionRunner`) overlays it on `DsState::gameSpecificMessage`
   and re-sends the DS state when it changes. It wins over the DS panel's manual game-message text.

## 10. Simplifications (honest list)

* No official CAD: dimensions outside the manual text come from the AprilTag layout and MapleSim (marked above);
  expect centimetre-level, not millimetre-level, agreement. The hub is a rectangular tube of the stated 47 in
  footprint and 72 in rim height - the hexagonal funnel, the hub's internal ramps/sensor array and the **back net**
  are not modelled (overshot shots simply fly on). Hub exit positions/velocities are MapleSim's, at an approximate height.
* Tower: base plate, uprights and rungs only (no support structure, no climb scoring / TOWER points / ranking points).
* Trench: arm + one post per side; the hinged pivot arm and electronics are not modelled. Wall/driver-station
  geometry is solid boxes.
* Bumps use the stated ridge/width/depth with a derived 0.5 in edge step; the ramp thickness is not modelled.
* Depot barrier and outpost positions (y) are from MapleSim/AprilTags to a few centimetres. Outposts: corral
  delivery and a timed human player only; the chute door, the human player throwing fuel at the hub and the 3-second
  scoring-table behaviour of the real field are not simulated.
* Fuel is a rigid sphere (no wear/deformation, no compression against the flywheel); exit speed is
  `omega x r x efficiency`, not a contact model.
* Pickup and shooter are idealised zones: a pickup absorbs any fuel centre inside its box (no mouth geometry or jamming),
  a shooter has no hopper/indexer physics (the feed is just its activation conditions); the shot ghost time (`shotGhostS`)
  stands in for the fuel clearing the robot's own shapes.
* A zone's pose uses the attachment link pose of the same tick for mechanisms that ticked earlier and the previous tick for
  later ones (list parents before children in `RobotConfig::mechanisms`).
* The game logic is for a single robot (`SimContext::chassisBody`); other robots would need their own meters.
* The AUTO winner is decided from fuel scored by the simulated alliances only (opponent fuel is whatever the user
  places), ties are seeded random as the real FMS.
