# ADR 0001 – Injecting the `halsim_wpiemu` HALSim extension into an unmodified robot project

Status: **Accepted (proven on Windows, WPILib/GradleRIO 2026.2.1)** · Spike: `spike-halsim`

## Decision

The emulator loads `halsim_wpiemu` into the robot process through WPILib's own
`HALSIM_EXTENSIONS` mechanism. The project is never edited.

* Java: `gradlew -I wpiemu-init.gradle simulateJava` (also works for `simulateJavaDebug`).
* C++: `gradlew -I wpiemu-init.gradle simulateNative`.
* **Preferred for process control** (no Gradle in the run path, fast restarts, the emulator
  owns the PID): run `gradlew simulateExternalJavaRelease` / `simulateExternalNativeRelease`
  once as a *build + describe* step, then launch the JVM / exe ourselves with
  `HALSIM_EXTENSIONS=<abs path to halsim_wpiemu>`. Both paths were proven.
* The extension is also the **sim-clock master** (`HALSIM_PauseTiming` + `HALSIM_StepTiming`
  driven by the emulator).

## How it works (verified against the 2026.2.1 sources and by running it)

1. `HAL_Initialize()` (sim HAL, `hal/src/main/native/sim/HAL.cpp`) ends with
   `HAL_LoadExtensions()` (`Extensions.cpp`). It splits env `HALSIM_EXTENSIONS` on `;`
   (Windows) / `:` (Linux, macOS), and for each entry does `LoadLibraryA` / `dlopen`, looks up
   the C symbol **`HALSIM_InitExtension`** (`int (*)(void)`) and calls it.
   Return `0` = ok, `>0` = non-fatal (library is unloaded), `<0` = abort HAL init.
   * On POSIX, if `dlopen(path)` fails it retries `lib<path>.so` / `lib<path>.dylib`.
     Always pass the **absolute full filename**.
2. HAL init runs *before* any robot device exists, so callbacks registered in
   `HALSIM_InitExtension` see every device creation. Java reaches it via `HAL.initialize`
   (JNI `wpiHaljni.dll` → `wpiHal.dll`); C++ via `frc::StartRobot` → `HAL_Initialize`.
3. **Same HAL instance:** the Java JNI lib and C++ robot both bind to the one `wpiHal` module in
   the process. The extension links against `wpiHal` (import lib `wpiHal.lib` from
   `edu/wpi/first/hal/hal-cpp/2026.2.1/hal-cpp-…-windowsx86-64.zip`, headers from `…-headers.zip`) and
   the loader resolves it to the already-loaded module, so `HALSIM_*` calls act on the robot's HAL.
   Build with `/MD` (same CRT as WPILib).
4. `HALSIM_InitExtension` runs on the robot's main thread inside `HAL_Initialize`
   (holding its init mutex; re-entrant `HAL_*` calls are fine, blocking is not).

### GradleRIO gotcha: env var alone is NOT enough

`simulateJava*` (`WPIJavaExtension.configureSimulationTask`) and `simulateNative*`
(`NativeSimulationTask.exec`) **overwrite** `HALSIM_EXTENSIONS` whenever at least one
`wpi.sim.add*()` extension has `defaultEnabled = true` – and the stock templates do
`wpi.sim.addGui().defaultEnabled = true`. So a user-set `HALSIM_EXTENSIONS` is lost for the
typical project. Other env vars (our IPC endpoint etc.) pass through untouched
(Gradle client → daemon → forked process inherit the environment; verified).

Fix, with no project edit: a Gradle **init script** (`-I`, command-line only; do *not* put it in
`~/.gradle/init.d` – that would affect all the user's builds). In `afterEvaluate` it
(a) sets `defaultEnabled=false` on all `wpi.sim.halExtensions` (so GradleRIO stops overriding), and
(b) sets `HALSIM_EXTENSIONS` on every `JavaSimulationTask` / `NativeSimulationTask`.
Doing it at configuration time (not in `doFirst`) is independent of action ordering
(`doFirst` actions registered later run *earlier*, GradleRIO's would run after ours).
Consequence: the stock Sim GUI (`halsim_gui`) is not loaded – desired, the emulator replaces it.
`halsim_ds_socket` (real DS) is intentionally not supported: the emulator's built-in Driver Station
feeds joysticks and DS state through the same HALSIM APIs (`HALSIM_SetJoystick*`, `NotifyDriverStationNewData`).

```groovy
// wpiemu-init.gradle  (generated by the emulator into its app-data dir, passed with -I)
def emuExt = System.getenv('WPIEMU_EXT')           // absolute path of halsim_wpiemu.{dll,so,dylib}
allprojects { p ->
    p.afterEvaluate {
        def wpi = p.extensions.findByName('wpi')
        if (wpi == null) return
        wpi.sim.halExtensions.each { it.defaultEnabled.set(false) }
        p.tasks.matching {
            def n = it.class.name   // class names carry a _Decorated suffix -> startsWith
            n.startsWith('edu.wpi.first.gradlerio.simulation.JavaSimulationTask') ||
            n.startsWith('edu.wpi.first.gradlerio.simulation.NativeSimulationTask')
        }.configureEach { t -> t.environment('HALSIM_EXTENSIONS', emuExt) }
    }
}
```

Exact commands used (PowerShell; `JAVA_HOME` = `C:\Users\Public\wpilib\2026\jdk`; the project's own
`settings.gradle` already resolves GradleRIO from the offline `…\wpilib\2026\maven`):

```powershell
$env:WPIEMU_EXT   = 'C:\path\to\halsim_wpiemu.dll'
$env:WPIEMU_CLOCK = 'master'                      # our own switch, passed through to the extension
.\gradlew.bat --no-daemon --console=plain -I C:\path\wpiemu-init.gradle simulateJava     # or simulateNative
```

### Alternative: `simulateExternal*` + direct launch (recommended for the run loop)

`gradlew simulateExternalJavaRelease` builds the fat jar + extracts JNI libs and writes
`build/sim/release_java.json`; `simulateExternalNativeRelease` writes `build/sim/release_native.json`
(also `…Debug`). Fields: Java `{libraryDir, mainClassName, environment, extensions[]}`; native
`{launchfile (exe), libpaths, environment, extensions[]}`. Then, no Gradle involved:

```powershell
$env:HALSIM_EXTENSIONS = 'C:\path\halsim_wpiemu.dll'
# Java (jar = build\libs\<rootProject>.jar, Main-Class in manifest; on macOS add -XstartOnFirstThread)
& $jdk\bin\java.exe "-Djava.library.path=<libraryDir>" -jar build\libs\<name>.jar
# C++ (launchfile = build\install\frcUserProgram\windowsx86-64\release\lib\frcUserProgram.exe)
& <launchfile>      # working dir = project dir; dlls sit next to the exe
```
Merge `environment` from the JSON into the child env. Trade-offs: loses project-specific
`JavaExec` customisation (jvmArgs, working dir) but the emulator owns the PID (kill by PID,
no orphaned `cmd → java client → single-use daemon → cmd → exe` chain) and iterates faster.

## Device observation (proven: Java Shelby project + hand-written C++ project)

All through `hal/simulation/*Data.h` (C API, header-only to us, symbols exported by `wpiHal`).
There is no "device created" event stream; each family exposes **per-index
`Register<Family>InitializedCallback(index, HAL_NotifyCallback, param, initialNotify)`**, so
register for every index `0..HAL_GetNum*()-1` (from `hal/Ports.h`) with `initialNotify=true`.

* Callback type: `void(const char* name, void* param, const HAL_Value* v)`; use `v->data.v_boolean`.
* `initialNotify=true` fires immediately for **every** index with its current value (mostly
  `false`) – keep a per-channel `live` flag and only report transitions (`true` = created, `false` = freed).
* Callbacks run **synchronously on the robot thread inside the HAL init call** (e.g. inside the
  `PWMSparkMax` constructor). Never block, never call `HALSIM_StepTiming`/`WaitForProgramStart`
  there; copy data and queue it for the IPC thread.

| Family | Register | Notes |
|---|---|---|
| PWM | `HALSIM_RegisterPWMInitializedCallback(ch,…)`; values `HALSIM_Get/SetPWMSpeed` (-1..1), `…PulseMicrosecond`, `…Position`, `…PeriodScale` | robot output → read `Speed` (verified 0.5 read back). Register `RegisterPWMSpeedCallback` on creation to get changes. |
| DIO | `HALSIM_RegisterDIOInitializedCallback`; `HALSIM_Get/SetDIOValue`, `HALSIM_GetDIOIsInput` | write inputs with `SetDIOValue` (verified: robot saw `false`). |
| AnalogIn | `HALSIM_RegisterAnalogInInitializedCallback`; `HALSIM_Get/SetAnalogInVoltage` | verified 3.3 V visible to robot. |
| Encoder | `HALSIM_RegisterEncoderInitializedCallback(idx)`; `HALSIM_GetEncoderDigitalChannelA/B(idx)`, `HALSIM_Set/GetEncoderCount/Distance/Rate/Period/Direction/DistancePerPulse` | encoder index ≠ DIO channel; DIO A/B channels also appear as DIO devices. Verified `SetEncoderCount`. |
| Relay | `HALSIM_RegisterRelayInitializedForwardCallback` / `…ReverseCallback(idx)`; `HALSIM_GetRelayForward/Reverse` | one index per header; fwd/rev separate. |
| CTRE PCM | `HALSIM_RegisterCTREPCMInitializedCallback(module)`; `HALSIM_RegisterCTREPCMSolenoidOutputCallback(module, ch,…)`, `HALSIM_GetCTREPCMSolenoidOutput`, `…CompressorOn/Current/ClosedLoopEnabled` | verified output read (ch 5 = true). |
| REV PH | `HALSIM_RegisterREVPHInitializedCallback`; same shape as PCM | |
| PDP/PDH | `HALSIM_RegisterPowerDistributionInitializedCallback` | |
| RoboRIO | `HALSIM_Get/SetRoboRioVInVoltage` (battery), `…TeamNumber`, … | battery model write target. |
| **SimDevice** | `HALSIM_RegisterSimDeviceCreatedCallback(prefix, param, cb, initialNotify)`, `HALSIM_EnumerateSimDevices`, `HALSIM_EnumerateSimValues(dev, …)`, `HALSIM_Register/Get/SetSimValue…` (`hal/SimDevice.h`) | **How Phoenix 6 shows up**, plus NavX/ADIS/etc. Values have a direction (`0`=input→we write, `1`=output←robot, `2`=bidir). |
| CAN | `HALSIM_RegisterCanSendMessageCallback(cb, param)`: `(name, param, arbId, data, size, periodMs, *status)`; `HALSIM_RegisterCanReceiveMessageCallback`: `(name, param, *arbId, mask, data, *size, *timestamp, *status)`; also OpenStream/ReadStream/GetCANStatus | 2026.2.1 has **no bus id** in these callbacks. Decode arbId: devId = `id&0x3F`, api = `(id>>6)&0x3FF`, mfr = `(id>>16)&0xFF`, devType = `(id>>24)&0x1F`. To *answer* a receive request: match `(want & mask)==(*id & mask)`, then write `*id,data,*size (≠42),*timestamp` and `*status=0` (verified round trip, 150/150 frames). |

### Phoenix 6 finding (relevant to the Phoenix spike)

Phoenix 6 does **not** use `HALSIM_RegisterCan*` in sim (CAN tx/rx counters stayed 0 for
Shelby). The CTRE native sim DLLs (`CTRE_Phoenix6_Sim.dll`, `CTRE_SimProTalonFX.dll`, … extracted next
to the JNI libs) publish **HAL SimDevices** instead. The Shelby project (28 devices) enumerated at
startup, before the first loop:
`CANMotor:Talon FX (v6)[<id>]` (+ child devices `CANEncoder:…/Rotor Sensor`, `CANDIO:…/Fwd Limit`,
`CANDIO:…/Rev Limit`), `CANEncoder:CANcoder (v6)[<id>]`, `CANGyro:Pigeon 2 (v6)[<id>]`,
`CAN:CANrange (v6)[<id>]`. Values seen (type double):
Talon FX `supplyVoltage`(in), `dutyCycle`/`motorVoltage`/`torqueCurrent`/`supplyCurrent`(out);
CANcoder `supplyVoltage`, `position`(out), `rawPositionInput`, `velocity`; Pigeon 2 `supplyVoltage`,
`yaw`(out), `rawYawInput`, `pitch`, `roll`, `angularVel{X,Y,Z}`. (CANivore bus is not part of the name.)
This gives name→(model, CAN id) discovery for free and a documented read/write surface;
see the Phoenix ADR for the final mapping.

## Sim-time control (proven)

`hal/simulation/MockHooks.h` (2026.2.1 signatures; **times are µs**, the FPGA-time unit):

```c
void     HALSIM_PauseTiming(void);   void HALSIM_ResumeTiming(void);   HAL_Bool HALSIM_IsTimingPaused(void);
void     HALSIM_RestartTiming(void);
void     HALSIM_StepTiming(uint64_t delta_us);       // synchronous: waits for notifiers
void     HALSIM_StepTimingAsync(uint64_t delta_us);  // doesn't wait for robot loop
void     HALSIM_WaitForProgramStart(void);           // blocks until robot code called observeUserProgramStarting
void     HALSIM_SetProgramStarted(void);  HAL_Bool HALSIM_GetProgramStarted(void);
int32_t  HALSIM_RegisterSimPeriodicBeforeCallback / …AfterCallback(void(*)(void*), void*);   // per robot-loop iteration
```

Pattern used (works identically for Java and C++):

1. In `HALSIM_InitExtension`: `HALSIM_PauseTiming()` – FPGA time and all Notifiers freeze before
   robot code exists; spawn a clock thread.
2. Clock thread: `HALSIM_WaitForProgramStart()` (set by `HAL_ObserveUserProgramStarting`, i.e. after
   the robot constructor finished and all devices are created ⇒ the **discovery-complete signal**).
   Then drive: `HALSIM_StepTiming(5000)` per physics tick.
3. `HALSIM_StepTiming` splits the delta at each Notifier timeout, wakes expired notifiers and
   **waits until they re-enter `HAL_WaitForNotifierAlarm`**, i.e. the entire `TimedRobot` loop body
   (periodic + `simulationPeriodic`) has completed before it returns ⇒ strict lockstep:
   600 × 5 ms steps produced exactly 150 robot loops (20 ms period) and FPGA dt = 3 000 000 µs.
   3 s of sim took 2 ms (C++) / ~250 ms (Java, JIT warm-up) of wall time – faster than real time.
4. Sensor/actuator exchange: after each `StepTiming` returns the robot is quiescent, so it is safe to read
   outputs (`HALSIM_GetPWMSpeed`, SimDevice outputs) and write inputs (verified: `SetDIOValue`,
   `SetAnalogInVoltage`, `SetEncoderCount` were all seen by the robot in the next loop).
   For free-running (real-time) mode simply `HALSIM_ResumeTiming()`.
5. Driver Station: no DS GUI is loaded, so the extension is the DS: `HALSIM_SetDriverStationDsAttached(true)`,
   `…Enabled(true)`, `…Autonomous/Test`, `…AllianceStationId`, `…MatchTime`, joysticks
   `HALSIM_SetJoystickAxis/Button/POV/…Count`, then `HALSIM_NotifyDriverStationNewData()` (enabled
   robot ran teleop immediately – "Default TeleopPeriodic() method…" printed).

Rules/gotchas:
* `HALSIM_StepTiming` and `HALSIM_WaitForProgramStart` must run on the extension's **own thread**, never in a
  HAL callback or `HALSIM_InitExtension` (deadlock / blocks robot init).
* Robot code that busy-waits on FPGA time (`Timer.delay`, `Thread.sleep` is fine) will hang while paused
  unless someone steps.
* If the emulator dies, the robot freezes while paused: the extension must `HALSIM_ResumeTiming()` (or exit)
  on IPC disconnect; also register `HAL_OnShutdown(param, fn)` for cleanup.
* **2027 / allwpilib `main` API differs** (namespaces `wpi::hal`, headers `wpi/hal/…`,
  `HALSIM_WaitForProgramStart(HAL_Bool)`, `HALSIM_SetProgramStarted(HAL_Bool)`, `HALSIM_StepTiming(int64_t)` in
  nanoseconds, CAN callbacks gain a bus). Wrap these in one `halsim_compat.h` keyed on the GradleRIO year;
  everything above is **2026.2.1**.

## Gotchas

* **Use `HAL_GetNum…` counts, not literals** (e.g. 63 power-distribution indices exist in the sim HAL) and expect the `initialNotify` flood described above.
* `defaultEnabled` handling above; the init script has to match both Release and Debug tasks.
* `simulateNative` run chain is `gradle client → single-use daemon (with --no-daemon) → cmd(.bat run script) → frcUserProgram.exe`;
  killing Gradle doesn't reliably kill the exe. Have the extension send `GetCurrentProcessId()` / `getpid()` in its IPC hello so the
  emulator can kill the robot by PID (Gradle then exits by itself). Gradle daemons are shared with the user's other
  builds – never kill them by name.
* `NT: Listening on NT3 port 1735, NT4 port 5810` – fixed ports; two simulated robots (or a robot + real sim) on one machine
  collide ("address already in use"; the robot still runs but without NT). Single robot per machine in v1.
* Windows: `HALSIM_InitExtension` must be `__declspec(dllexport)` + `extern "C"` (the lookup is by undecorated name). Link with
  the MSVC `/MD` runtime. MSVC needs `vcvars64.bat` in the same `cmd` process as `cl`.
  Extension (and everything else) must be 64-bit.
* Both the Java and native paths print `HAL Extensions: Attempting to load: halsim_wpiemu` / `Successfully loaded extension`
  – a handy success marker for the launcher to parse. A missing/bad lib only prints a failure line; robot code keeps running
  *without* the extension (it will not time-sync) → launcher must verify the IPC hello within a timeout.
* Sim GUI (`halsim_gui`) is not needed for program-start: only `HAL_ObserveUserProgramStarting` sets it, so our clock thread must not
  call `HALSIM_SetProgramStarted` itself.
* macOS Java sim needs `-XstartOnFirstThread` (GradleRIO adds it; add it yourself when launching directly).

## Cross-platform notes (only Windows executed in this spike)

| | Windows | Linux | macOS |
|---|---|---|---|
| Extension file | `halsim_wpiemu.dll` | `libhalsim_wpiemu.so` | `libhalsim_wpiemu.dylib` |
| `HALSIM_EXTENSIONS` separator | `;` | `:` | `:` |
| HAL lib | `wpiHal.dll` (+`.lib`) | `libwpiHal.so` | `libwpiHal.dylib` |
| JNI/native extract dir | `build/jni/{release,debug}` (Java), `build/install/<comp>/<plat>/<type>/lib` (C++) | same | same |
| GradleRIO platform dir/zip | `windowsx86-64` | `linuxx86-64` | `osxuniversal` |

Unverified risk for Linux/macOS: Java loads JNI libs `RTLD_LOCAL`, so the extension must carry a normal
`DT_NEEDED`/install-name dependency on `libwpiHal` and be able to resolve it to the already-loaded copy
(`RPATH`/`LD_LIBRARY_PATH`/`DYLD_LIBRARY_PATH` pointing at the JNI extract dir – the init script can set it via
`t.environment`), otherwise a second private HAL copy could be loaded and silently observe nothing. Add a CI smoke test
that asserts the "device created" log for a canned project on each OS.

## Recommendations for IPC / time-sync design

* The extension is a thin, **single-threaded-from-IPC** shim: callbacks (robot threads) push events into a lock-free/ mutex-guarded
  queue; one IPC thread owns the socket; one clock thread owns `Step/Wait`. Never do socket I/O inside a HAL callback.
* Handshake message from extension: protocol version, `pid`, WPILib/GradleRIO year, runtime (Java/C++), HAL port counts. Emulator replies
  with clock mode (`master`|`realtime`), step size (suggest 5 ms ⇒ 200 Hz; must divide 20 ms evenly for lockstep;
  default `TimedRobot` period is 20 ms, `addPeriodic` periods are honoured because StepTiming stops at every notifier timeout).
* Tick protocol (clock master = emulator): `Tick{dt_us, sensorFrame}` → extension writes sensor inputs, `HALSIM_StepTiming(dt)`, collects actuator
  outputs (PWM speeds, SimDevice outputs, solenoids, relays, DIO outputs, CAN frames seen) → `ActuatorFrame` back. One round trip per step;
  keep it < 1 ms with shared memory or a local socket. Emulator may batch several steps/frame for faster-than-real-time.
* Discovery = diff of `Created/Freed` events up to `HALSIM_GetProgramStarted()`; later devices (lazy construction) still arrive via the
  same callbacks (`DeviceAnnounce` anytime). Keep the per-index `live` flags in the extension and re-announce on reconnect.
* Use `HALSIM_RegisterSimPeriodicAfterCallback` as an optional "robot loop finished" marker (fires once per `IterativeRobotBase` loop; in 2026 for
  `TimedRobot` – proven 150 calls / 3 s) if loop-synchronous sampling is wanted.
* Unmapped device loopback (plan M1) = the extension itself copies the output to the input (`dutyCycle→…`, DIO write-back) without an IPC hop.
* Launcher: build via `simulateExternal*` (parse the JSON), spawn the robot ourselves, set `WPIEMU_*` env (socket name, clock mode), watch stdout for
  `HAL Extensions: Successfully loaded` and the IPC hello; fallback to `gradlew -I` when the project has custom run config.

## Reference snippet (condensed from the working spike; MSVC: `cl /std:c++17 /EHsc /O2 /LD /MD /I<hal-headers> /I<wpiutil-headers> ext.cpp /link wpiHal.lib`)

```cpp
extern "C" __declspec(dllexport) int HALSIM_InitExtension(void) {
  for (int i = 0; i < HAL_GetNumPWMChannels(); i++)
    HALSIM_RegisterPWMInitializedCallback(i, OnInit, new Fam{"PWM", i, false}, /*initialNotify*/ true);
  // … DIO, AnalogIn, Encoder, Relay fwd/rev, CTREPCM, REVPH, PowerDistribution likewise …
  HALSIM_RegisterSimDeviceCreatedCallback("", nullptr, OnSimDevice, true);   // Phoenix 6, NavX, …
  HALSIM_RegisterCanSendMessageCallback(OnCanSend, nullptr);
  HALSIM_RegisterCanReceiveMessageCallback(OnCanRecv, nullptr);
  HALSIM_PauseTiming();                                   // we are the clock master
  std::thread([] {
    HALSIM_WaitForProgramStart();                         // robot constructed, devices created
    HALSIM_SetDriverStationDsAttached(true); HALSIM_SetDriverStationEnabled(true);
    HALSIM_NotifyDriverStationNewData();
    for (;;) { /* recv Tick from emulator, write inputs */ HALSIM_StepTiming(5000); /* send outputs */ }
  }).detach();
  return 0;
}
```
