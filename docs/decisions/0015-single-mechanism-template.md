# ADR 0015 - One core mechanism template

- Status: accepted
- Scope: `core/mechanisms`, editor (catalog, tree menu), game plugin wrappers

## Context

Core registered eight templates (roller, generic 1-DOF, intake, shooter, hood/pivot, turret, elevator,
indexer). Seven built the same one-axis `MechanismAxis`; they differed in defaults, a link name and a few
extra published values. A flywheel, a roller and a belt are one rotary machine, a hood and an arm are one
gravity-loaded pivot, an elevator and a climber are one linear stage. The eighth (intake) was two axes plus
game semantics ("active when deployed"), and beam breaks were generated by templates although they are not
a property of a mechanism. Users had to know which of many names matched their machine, and the editor needed
a palette panel to list them.

## Decision

- Core registers **one** template, `mechanism`, with **Motion** `rotary | arm | linear`. Everything else is
  properties: gear ratio, motor count, inertia / mass / length, stops (equal stops = continuous), gravity.
  The slots are `motor`..`motor8`, `encoder`, `velocitySensor`, `reverseLimit`, `forwardLimit`; the link is
  `mover`; published values are `position`, `velocity`, `voltage`, `current`, `atLowerLimit`, `atUpperLimit`.
- **Intake is removed from core.** An intake is a rotary roller mechanism (plus an arm mechanism if it
  deploys). The season plugin's wrappers (`game_2026.fuel_intake`) compose mechanisms by id.
- **Beam breaks are removed from core mechanisms** (slots, window properties, `WindowBeamBreakModel`). A year
  plugin writes digital slots from the state it reads.
- The editor has no catalog panel: **Add mechanism** lives in the tree's right-click menus (robot, chassis,
  mechanism). Configure's **Type** is the Motion (Rotary / Arm / Linear); templates cannot be switched in the editor, and the
  menus list core templates only. Plugin templates (Fuel intake / Fuel shooter) are added from the game plugin node's menu.
- Pre-release (ADR 0013): the old type keys (`roller`, `pivot`, `turret`, ...) are simply gone, with no
  migration; projects that use them fail validation with "unknown mechanism type".

## Consequences

- One code path to test and document ([mechanisms.md](../mechanisms.md) section 4).
- Plugins that read `rollerVelocity`, `deployed` or `surfaceSpeed` must read `velocity` / `position` of a plain
  mechanism instead (the 2026 plugin's defaults already do).
- The plant registry keeps its `flywheel` / `turret` / `elevator` keys for plugins that name them; the core
  template picks `dc_motor` (rotary), `arm` or `elevator` from Motion.
