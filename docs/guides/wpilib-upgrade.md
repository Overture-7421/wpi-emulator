# Upgrade WPILib for a new season

Read this when adding a WPILib season or updating the WPILib/Java toolchain pins.
Prerequisites: [Building](../BUILDING.md), [Releasing](../releasing.md#version-pins), and a
WPILib installation or generated project for the target season.

This checklist keeps season facts in one source of truth and confirms each value against both
WPILib's generated project/toolchain and the emulator code that consumes it. Do not infer a new
season's Java major or artifact version from the prior season.

## Establish the upstream toolchain

Before editing pins, create or inspect a project generated by the target season's WPILib tools.
Record the GradleRIO version, wrapper Gradle version, Java major used by WPILib, and available
desktop HAL/wpiutil artifacts. Verify these against that season's WPILib release notes and
installation rather than treating the emulator's current defaults as upstream facts.

The emulator determines the project year from the GradleRIO version, falling back to
`.wpilib/wpilib_preferences.json` or `settings.gradle`; this is implemented by
[ProjectInspector](../../core/runtime/src/launcher/project_inspector.cpp). Its CMake integration
uses the `wpilib` version for `hal-cpp` and `wpiutil-cpp`, with `ntcore-cpp` and `wpinet-cpp`
optional for vision ([WPILib discovery](../../halsim_ext/cmake/WpiEmuWpilib.cmake)).

## Update the pins and Java policy

1. Edit [`versions.json`](../../versions.json), the pin source read by
   [`WpiEmuVersions.cmake`](../../cmake/WpiEmuVersions.cmake).
   - Set `wpilib` to the version consumed by the emulator's HAL/wpiutil artifacts.
   - Update the GradleRIO version in every sample robot build script to the target season's
     generated value. `check_versions.py` enforces that these values match the `wpilib` pin.
   - Add the season year and its verified Java major to `jdk.seasons`. The generated toolchain
     pins, produced by [`app/common/CMakeLists.txt`](../../app/common/CMakeLists.txt), feed
     `ToolchainProvisioner::javaMajorForSeason`; an unlisted season intentionally has no
     managed-Java download.
2. If the Java major is new, add a `jdk.assets` entry for each supported platform/architecture:
   `windows-x64`, `linux-x64`, `macos-x64` and `macos-arm64`. Use the correct Temurin release
   archive URL, exact version, SHA-256 and byte size. The downloader verifies the hash, and
   [`check_versions.py`](../../tools/check_versions.py) requires GitHub URLs, matching version
   text, a 64-character hash, a size no greater than 500 MiB, and an asset for every mapped season
   and platform.
3. If the new season changes Java/Gradle compatibility, update the Java-to-Gradle compatibility
   table in [`jdk_policy.cpp`](../../core/runtime/src/launcher/jdk_policy.cpp) from Gradle's
   compatibility data. This table determines the maximum Java accepted for a project's wrapper;
   the season mapping determines the minimum.
4. If WPILib changes its Windows Visual C++ runtime requirement, update both
   `versions.json.msvcRuntimeMin` and `kMinVcRuntime` in
   [`jdk_policy.h`](../../core/runtime/include/wpiemu/core/launcher/jdk_policy.h). The version
   checker verifies that duplicate value.
5. Update any season-year paths or expected versions in the build, release workflow and samples.
   Keep the developer version in `CMakeLists.txt` a placeholder; release automation supplies the
   distributable version.

## Validate from a clean build

Run from the repository root:

```powershell
python tools\check_versions.py
python tools\check_wpilib_configure.py --generator "Visual Studio 17 2022" --architecture x64
cmake --preset windows-vs2022 -DWPIEMU_WPILIB_ROOT="C:\Users\Public\wpilib\<year>\maven" -DWPIEMU_WPILIB_DOWNLOAD=OFF
cmake --build --preset windows-vs2022-release --parallel
ctest --preset windows-vs2022-release
```

Use a fresh build tree or explicitly pass the new `WPIEMU_WPILIB_VERSION`: an existing CMake cache
retains its prior value. Confirm configuration reports real HAL and, when vision is in scope,
ntcore; a no-HAL stub is not an integration result. Also build the Java and C++ sample projects
with that season's WPILib tooling. When available, run the opt-in robot-project integration tests
from [Building](../BUILDING.md#opt-in-robot-project-tests); a skipped test does not validate the
robot process.

On Linux/macOS use the `Ninja` generator in `check_wpilib_configure.py` and the platform build/test
presets. A successful configure or fake-based test does not establish vendor firmware behavior or
native robot loading.
