# Upgrade WPILib for a new season

Read this when adding a WPILib season, bumping a WPILib or vendor-library version, or updating the
Java/Visual C++ toolchain pins.
Prerequisites: [Building](../BUILDING.md), [Season packs](../reference/seasons.md),
[Releasing](../releasing.md#version-pins), and a WPILib installation or generated project for the
target season.

Season facts live in one place, the season pack `seasons/<year>/season.json`. This checklist keeps
them there and confirms each value against both WPILib's generated project/toolchain and the
emulator code that consumes it. Do not infer a new season's Java major, artifact version or HAL
layout from the prior season.

## Establish the upstream toolchain

Before editing a manifest, create or inspect a project generated by the target season's WPILib
tools. Record the GradleRIO version, wrapper Gradle version, Java major used by WPILib, the install
folder name, and the available desktop HAL/wpiutil/ntcore artifacts. Verify these against that
season's release notes and installation rather than the emulator's current defaults.

The emulator determines the project year from the GradleRIO version, falling back to
`.wpilib/wpilib_preferences.json` or `settings.gradle`
([ProjectInspector](../../core/runtime/src/launcher/project_inspector.cpp)). The season pack of that
year selects the extension, launch profile, Java and install folder.

## Choose the scenario

| You are doing | Edit |
|---|---|
| A patch release of a known season | `wpilib.version` and `wpilib.verified` in the manifest, then each sample's GradleRIO version |
| A preview revision (alpha, beta) | The same, plus `wpilib.installFolder` when the installer folder changes; a newer suffixed folder is found without it |
| A vendor-library release (PhotonLib) | `vendors.<vendor>.verified` (and `defaultVersion`); no code change when the wire schema is unchanged |
| A new year whose HAL is the same generation | A new `seasons/<year>/` pack naming the existing `platform.abi`; no C++, CMake or workflow edit |
| A new year with a new HAL generation | A new ABI profile and its per-ABI sources (below), then the pack |

An unverified version of a known season is not refused: the emulator warns and runs on a best-effort
basis ([version policy](../reference/seasons.md#version-policy)). Listing a version in `verified` is how
you record that you checked it.

## Update an existing season

1. Edit `seasons/<year>/season.json`: `wpilib.version` (the artifact version the extension builds
   against; it must also appear in `wpilib.verified`) and the verified list.
2. Update each sample listed in `samples` to the same GradleRIO version.
   [`check_seasons.py`](../../tools/check_seasons.py) compares them.
3. Run `python tools\check_seasons.py` and `python tools\check_versions.py`.
4. Rebuild from a fresh tree (a cached `WPIEMU_WPILIB_VERSION` survives otherwise) and run the
   season's real-HAL and robot tests.

## Add a season on an existing HAL generation

1. Copy `seasons/_template/season.json` to `seasons/<year>/season.json`. Set `year`, `channel`,
   the WPILib pin and `installFolder`, `toolchain.javaMajor`, `platform.abi` and `platform.launch`
   (reuse the previous season's values when the generation is unchanged), the vendor schema and
   verified versions, and the `samples` (and `probes`, if the season has probe samples).
   Leave `"default": false` unless this season becomes the default.
2. Add a sample robot project per language under `samples/` and list them in `samples`.
3. If the Java major is new, add a `jdk.assets` entry for each platform in
   [`versions.json`](../../versions.json): the correct Temurin archive URL, exact version, SHA-256
   and byte size ([`check_versions.py`](../../tools/check_versions.py) requires an asset for every
   season and platform). If it changes Java/Gradle compatibility, update the table in
   [`jdk_policy.cpp`](../../core/runtime/src/launcher/jdk_policy.cpp).
4. If WPILib changes its Windows Visual C++ runtime requirement, update `msvcRuntimeMin` in
   `versions.json` and `kMinVcRuntime` in
   [`jdk_policy.h`](../../core/runtime/include/wpiemu/core/launcher/jdk_policy.h).
5. For a game plugin, copy `seasons/_template/game` to `seasons/<year>/game`, set
   `"game": {"plugin": "game_<year>"}` and follow the [game plugin guide](game-plugins.md).
   A season without game rules keeps `"game": null` and runs core-only.

No other file changes: CMake, the toolchain pins, the install layout checks and the CI/release
workflows read the season list from the manifests (`WPIEMU_SEASONS=all`).

## Add a new HAL generation

Only a genuinely new HAL (renamed headers, changed types or units, removed or added device
families) needs code:

1. Add `seasons/abi/<id>.json`: Maven groups, header probes, `cxxStandard`, `ntcoreRequired` and, if
   ntcore loads it, the `datalog` group.
2. Add `hal_abi/<id>/include/wpiemu/hal_abi/` with `hal_includes.h`, `hal_time.h`, `nt_includes.h` and
   `sim_device_includes.h`.
3. Add the per-ABI sources: `halsim_ext/src/hal/abi/<id>/hal_platform_abi.cpp` and
   `bridges/hal/src/abi/<id>/hal_sim_abi.cpp`, implementing the interfaces of `hal_platform_abi.h`
   and `hal_sim_abi.h`. Families the HAL no longer has are null in the ABI factory and omitted, never
   faked.
4. Add the real-HAL suites under `halsim_ext/tests/hal/abi/<id>` (and `bridges/hal/tests/abi/<id>`).
5. Audit clock units as well as symbol names: bridge interfaces use microseconds, so convert at the
   HAL boundary. Re-verify vendor desktop artifacts separately from hardware dependencies. For
   PhotonLib, compare the generated metadata, target and multi-tag schemas and test each language's
   actual decoder with its version checks enabled; a Java pass does not prove C++ compatibility (see the
   [pinned preview's upstream C++ blocker](../reference/bridges.md#photonvision)). A new PhotonLib wire
   format also needs a named schema in the vision encoder.
6. Add a launch profile in core only if Gradle behaves differently from the existing two.

[`check_boundaries.py`](../../tools/check_boundaries.py) and `check_seasons.py` fail when a module
names a year or ABI outside its `abi/<id>` sources.

## Validate from a clean build

Run from the repository root, selecting the target season explicitly:

```powershell
python tools\check_seasons.py
python tools\check_versions.py
python tools\check_wpilib_configure.py --generator "Visual Studio 17 2022" --architecture x64
cmake --preset windows-vs2022 -DWPIEMU_WPILIB_SEASON=<year> -DWPIEMU_WPILIB_ROOT="C:\Users\Public\wpilib\<install folder>\maven" -DWPIEMU_WPILIB_DOWNLOAD=OFF
cmake --build --preset windows-vs2022-release --parallel
ctest --preset windows-vs2022-release
```

Use a fresh build tree when changing seasons so cached headers and libraries cannot leak across
seasons. `WPIEMU_WPILIB_VERSION` remains available for an intentional artifact-version override.
Confirm configuration reports real HAL and, when vision is in scope, ntcore; a no-HAL stub is not an
integration result. Also build the Java and C++ sample projects with that season's WPILib tooling. When
available, run the opt-in robot-project integration tests from
[Building](../BUILDING.md#opt-in-robot-project-tests); a skipped test does not validate the robot
process.

On Linux/macOS use the `Ninja` generator in `check_wpilib_configure.py` and the platform build/test
presets. A successful configure or fake-based test does not establish vendor firmware behavior or
native robot loading.
